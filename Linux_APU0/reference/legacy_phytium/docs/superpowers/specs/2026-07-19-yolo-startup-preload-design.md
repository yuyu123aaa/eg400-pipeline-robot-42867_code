# YOLO 启动预加载设计

## 目标

程序启动时同步加载 YOLO 模型，避免用户第一次点击“启动识别”时等待 ONNX Runtime 创建 Session。若 ONNX Runtime 在 Session 初始化阶段触发原生崩溃，崩溃应发生在网页服务启动之前，并通过即时刷新的阶段日志明确最后到达的位置。

## 方案

采用现有 `PRELOAD_YOLO` 配置开关，并将默认值设为 `True`。`main.start_background_services()` 保持以下顺序：

1. 调用 `init_yolo()` 创建并保存唯一的模型实例。
2. 模型加载成功后启动 UDP、建图、摄像头、手柄和温度线程。
3. 后台服务启动完成后才调用 Flask `app.run()`。

不创建额外 Session，不在后台线程异步加载，也不在首次识别请求中重复加载。

## 日志和失败行为

模型加载阶段至少输出以下即时刷新日志：

- 开始加载模型，并包含模型路径。
- ONNX Session 创建成功。
- 模型初始化全部完成。

ONNX Runtime 的 C++ `abort()` 无法被 Python `try/except` 捕获，程序会在启动阶段退出；最后一条已刷新的日志用于判断崩溃阶段。普通 Python 异常仍由现有异常处理记录，并使预加载返回失败。

预加载返回失败时不继续启动后台服务和 Flask，避免网页看似可用但识别功能不可用。

## 测试

自动化测试验证：

- 默认配置启用启动预加载。
- `init_yolo()` 在其他后台服务之前调用。
- 预加载失败时不启动其他服务。
- 关闭 `PRELOAD_YOLO` 时仍可跳过预加载，保留故障排查入口。

板端人工验证重复启动程序，记录每次最后一条阶段日志；后续再使用独立的单 Session/gdb 诊断定位 ONNX Runtime 原生越界。
