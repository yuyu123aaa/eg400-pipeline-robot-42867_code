# 飞腾派 ONNX 稳定运行与 YOLO 异步推理优化说明

## 1. 最终效果

项目仍然使用 `best.onnx` 模型，但不再使用 ONNX Runtime，而是由 OpenCV DNN 完成 ONNX 模型加载和推理。

经过飞腾派实际测试：

- YOLO 关闭时，摄像头画面约为 30 FPS。
- YOLO 开启时，摄像头画面仍约为 30 FPS。
- 视频延迟处于可以接受的范围。
- ONNX 模型能够在程序启动阶段完成加载和预热。
- 不再触发 ONNX Runtime 创建 Session 时的 C++ `std::vector` 越界断言。

需要注意：画面达到 30 FPS，并不代表模型每秒推理 30 次。当前实现将视频采集和模型推理解耦，使视频保持 30 FPS，而 YOLO 按飞腾派实际算力独立运行。

---

## 2. 为什么不再使用 ONNX Runtime

原来的 ONNX 模型通过以下方式加载：

```python
onnxruntime.InferenceSession(model_path)
```

在飞腾派上创建 ONNX Runtime Session 时会稳定触发：

```text
/opt/rh/gcc-toolset-12/root/usr/include/c++/12/bits/stl_vector.h:1123:
std::vector<_Tp, _Alloc>::operator[](size_type):
Assertion '__n < this->size()' failed.
已放弃
```

该错误具有以下特征：

- 发生在 ONNX Runtime Session 创建阶段。
- 尚未进入摄像头推理，程序就已经终止。
- 多次运行均可复现。
- 禁用 ONNX Runtime 图优化后仍然会发生。
- 同一个 `best.onnx` 可以被 OpenCV DNN 正常加载和推理。

因此可以判断：

1. `best.onnx` 并不是完全损坏或无法解析的模型。
2. 崩溃路径集中在飞腾派当前 ONNX Runtime 二进制的模型解析、图初始化或内部算子处理阶段。
3. 该问题可能与 ARM 环境、当前 ONNX Runtime 构建方式、GCC 12 STL 断言或特定模型图结构的组合兼容性有关。

在没有带调试符号的 ONNX Runtime 和完整 C++ 调用栈时，无法进一步证明具体是哪一个内部索引发生了越界。但可以确定崩溃点属于 ONNX Runtime 的原生 C++ 路径，而不是 Python 业务代码。

不建议通过关闭 `_GLIBCXX_ASSERTIONS` 强行隐藏错误。这样只能让断言不再立即终止程序，不能消除潜在的越界访问，反而可能将稳定崩溃变成随机错误或数据损坏。

---

## 3. 保留 ONNX，使用 OpenCV DNN

ONNX 是模型文件格式，ONNX Runtime 只是可以运行 ONNX 的引擎之一。

项目仍然使用：

```text
best.onnx
```

模型加载方式改为：

```python
self.net = cv2.dnn.readNetFromONNX(model_path)
self.net.setPreferableBackend(cv2.dnn.DNN_BACKEND_OPENCV)
self.net.setPreferableTarget(cv2.dnn.DNN_TARGET_CPU)
```

这样，模型图由 OpenCV DNN 负责解析和执行，不再进入会触发 GCC 断言的 ONNX Runtime 代码路径。

### 3.1 输入预处理

推理前的图像处理流程为：

```text
摄像头 BGR 图像
  → 缩放至 256 × 192
  → BGR 转 RGB
  → 像素值除以 255
  → 转换为 NCHW Float32 张量
  → OpenCV DNN forward()
```

对应代码使用：

```python
blob = cv2.dnn.blobFromImage(
    frame,
    scalefactor=1.0 / 255.0,
    size=(256, 192),
    mean=(0, 0, 0),
    swapRB=True,
    crop=False,
    ddepth=cv2.CV_32F,
)
```

### 3.2 输出后处理

飞腾派测试得到的模型输出形状为：

```text
(1, 9, 1008)
```

输出仍然经过原有后处理：

1. 读取候选框坐标。
2. 读取各类别置信度。
3. 按置信度阈值过滤。
4. 将中心点和宽高转换为左上角、右下角坐标。
5. 使用 NMS 去除重叠检测框。
6. 根据类别绘制不同颜色的检测框和英文标签。

因此，更换运行引擎不会改变模型类别、置信度、NMS 和画框业务逻辑。

## 4. 模型在程序启动阶段加载

原来的程序只有在第一次点击“启用识别”时才加载模型，因此第一次开启识别会长时间停顿。如果 ONNX Runtime 崩溃，崩溃也会发生在用户点击按钮之后。

现在的启动顺序为：

```text
启动 main.py
  → 加载 best.onnx
  → 创建 OpenCV DNN 网络
  → 使用全零张量预热一次
  → 模型初始化完成
  → 启动摄像头和其他后台服务
  → 启动网页
```

预热使用与模型输入相同尺寸的全零数据：

```python
warmup = np.zeros((1, 3, 192, 256), dtype=np.float32)
self.net.setInput(warmup)
self.net.forward()
```

这样可以：

- 在程序启动阶段发现模型加载问题。
- 避免第一次点击“启用识别”时再初始化模型。
- 提前完成 OpenCV DNN 第一次 `forward()` 的初始化工作。

---

## 5. 原同步推理为什么会造成卡顿

原摄像头线程中的处理流程为：

```text
读取摄像头
  → 缩放图像
  → YOLO forward()
  → 绘制检测框
  → JPEG 编码
  → 发布给网页
  → 读取下一帧
```

飞腾派实测一次 OpenCV DNN 推理大约需要：

```text
120 ms
```

同步执行时，摄像头线程每次推理都必须等待这 120 ms。在此期间无法读取下一帧，也无法向网页发布新画面。

这会造成：

- 视频周期性停顿。
- 摄像头驱动缓冲中的旧帧逐渐积压。
- 网页显示的画面越来越滞后。
- YOLO 关闭后画面明显更加流畅。

本质上，同步结构将视频帧率限制在了最慢处理步骤的速度上。

---

## 6. 使用独立 YOLO 工作线程

现在将摄像头处理和模型推理拆分为两个独立数据通路。

### 6.1 摄像头线程

```text
读取摄像头
  → 取得最近一次检测结果
  → 在当前画面绘制检测框
  → JPEG 编码
  → 发布给网页
  → 立即读取下一帧
```

### 6.2 YOLO 工作线程

```text
取得最新待检测帧
  → OpenCV DNN forward()
  → 保存最新检测结果
  → 等待下一张最新帧
```

摄像头线程不再直接调用：

```python
net.forward()
```

因此摄像头线程不会再等待模型推理完成。YOLO 工作线程负责后台推理，摄像头线程只读取它最近一次产生的检测结果。

对应实现位于：

```text
core/vision.py
```

其中 `_LatestYoloWorker` 负责后台推理和最新结果发布。

## 7. 视频30帧不等于模型推理30帧

一次推理约为 120 ms，因此理论推理上限约为：

```text
1000 ÷ 120 ≈ 8.3 次/秒
```

异步处理后的实际效果为：

- 摄像头画面约 30 FPS。
- YOLO 检测结果约每秒更新 8 次。
- 两次推理之间继续使用最近一次检测框。
- 视频不会等待检测结果。
- 检测框可能比实时画面晚约一两百毫秒，但延迟不会持续累积。

因此，开启 YOLO 后仍然显示 30 FPS，表示视频通路已经不再被推理通路阻塞，而不是模型本身达到了 30 FPS。

---

## 8. 为什么只保留一张待检测帧

如果摄像头每秒产生 30 帧，而模型每秒只能处理约 8 帧，普通队列每秒会积压大约 22 帧。

如果保存所有待识别帧：

```text
摄像头：1, 2, 3, 4, 5, 6, 7...
YOLO：  1......2......3......
```

运行时间越长，YOLO 识别的画面就越旧，最终可能识别几秒前的内容。

当前实现使用“单槽最新帧”：

```text
正在推理第1帧
等待位置保存第2帧
第3帧到达，用第3帧覆盖第2帧
第4帧到达，用第4帧继续覆盖
第1帧完成后，直接处理当前最新帧
```

该设计具有以下效果：

- 不会建立无限增长的推理队列。
- 内存不会因为待检测帧持续增加。
- YOLO 总是尽量处理最新图像。
- 模型速度较慢只会降低检测框刷新频率。
- 视频延迟不会随着运行时间持续增长。

YOLO 关闭或重新开启时，还会清除待处理帧和旧结果，避免关闭识别后继续发布之前的检测结果。

## 9. 从15帧恢复到30帧

为了降低摄像头缓冲延迟，曾尝试设置：

```python
cap.set(cv2.CAP_PROP_BUFFERSIZE, 1)
```

该设置在部分普通 PC 环境中可能有效，但在飞腾派当前 V4L2 摄像头驱动上产生了副作用。

只有一个驱动缓冲时，可能出现以下过程：

```text
摄像头填充唯一缓冲
  → Python 取走缓冲
  → 应用处理当前帧
  → 此时没有第二块缓冲接收下一帧
  → 下一帧被丢弃
```

飞腾派上的表现为：

```text
YOLO 关闭：约 15 FPS
YOLO 开启：约 15 FPS
修改前关闭 YOLO：约 30 FPS
```

由于 YOLO 开关两种状态下均稳定为 15 FPS，可以确定该回退位于公共摄像头路径，而不是模型推理路径。

后来撤销：

```python
CAP_PROP_BUFFERSIZE = 1
```

恢复 V4L2 默认的多缓冲策略后，摄像头重新达到约 30 FPS。

默认多缓冲没有重新造成明显延迟，是因为异步 YOLO 已经消除了摄像头线程中的 120 ms 推理阻塞，摄像头线程能够及时读取和处理缓冲中的画面。

## 10. 页面按需推流

前端现在只有以下页面连接视频流：

- 系统概览。
- 实时画面。

切换至以下页面时会断开 `/video_feed`：

- 巡检轨迹 GIS。
- 3D 姿态。
- 设备控制。
- PID 调参。
- 缺陷日志。
- 历史记录。

前端通过清空图像地址断开连接：

```javascript
img.src = "";
```

服务端会统计视频连接数量。没有网页观看视频时：

- 停止 JPEG 编码。
- 停止 MJPEG 网络传输。
- 摄像头仍可继续采集。
- YOLO 检测仍可继续运行。
- 缺陷自动记录功能仍然有效。

这样减少了无意义的 JPEG 编码、内存复制和网络传输开销。

## 11. 其他延迟优化

除异步推理外，还进行了以下处理：

### 11.1 YOLO 关闭时不缩放

YOLO 关闭时不再将每一帧缩放到 `256 × 192`，避免无用的 OpenCV 图像处理。

### 11.2 停止状态持续丢弃旧帧

系统处于停止状态时，通过：

```python
cap.grab()
```

持续取走摄像头旧帧。重新启动后不会先播放停止期间积压的历史画面。

### 11.3 禁止视频响应缓存

`/video_feed` 响应增加：

```text
Cache-Control: no-store, no-cache, must-revalidate, max-age=0
Pragma: no-cache
Expires: 0
X-Accel-Buffering: no
```

避免浏览器或代理缓存、缓冲 MJPEG 数据。

### 11.4 使用浏览器原生 MJPEG

网页继续使用原生：

```html
<img src="/video_feed">
```

避免 JavaScript 逐帧解析、Blob 创建和对象 URL 更新造成额外复制和延迟。

## 12. 最终数据通路

```text
                         ┌→ 单槽最新帧 → OpenCV DNN → 最新检测结果 ┐
摄像头约30 FPS → 采集线程 ┤                                       ├→ 绘制检测框
                         └───────────────────────────────────────┘
                                           ↓
                                       JPEG 编码
                                           ↓
                                      网页约30 FPS
```

最终优化目标不是强制让模型推理达到 30 FPS，而是：

> 视频保持约 30 FPS，模型按照飞腾派能够承受的速度独立运行，较慢的推理不会再阻塞视频。

## 13. 与 INT8 量化的关系

当前版本尚未进行 INT8 量化。

目前已经解决的是：

- ONNX Runtime 启动崩溃。
- 同步推理阻塞视频。
- 推理队列造成潜在延迟累积。
- 非视频页面产生无效 JPEG 编码和推流。
- 单帧 V4L2 缓冲导致帧率减半。

未来如果进行 INT8 量化，主要提升的是 YOLO 检测结果刷新速度。例如，模型推理可能从约 8 次/秒提升到更高频率，但视频通路本身已经能够维持约 30 FPS。

是否进行 INT8 量化，还需要分别验证：

- OpenCV DNN 对量化模型算子的支持情况。
- 飞腾派 CPU 是否能从 INT8 内核获得实际性能收益。
- 量化后检测精度是否可接受。
- 量化模型的输出结构是否仍与当前后处理兼容。

因此，INT8 属于后续模型推理优化，不是当前视频达到 30 FPS 的必要条件。
